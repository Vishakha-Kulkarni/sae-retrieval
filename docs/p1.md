# P1: learned impact scoring

The scorer sums positive contributions from shared query/document concepts.
Each contribution is a two-layer MLP over `log1p(query activation)`,
`log1p(document activation)`, IDF, and `log1p(document length / mean length)`.
Document length is the sum of its retained activations. No concept intersection
means score zero. Parameters are shared across concepts. The model learns using
listwise KL divergence to dense teacher scores over each query's candidates.

This is a concrete initial architecture, pending the team's exact specification.
It can be evaluated over posting-list matches because scores are additive;
this implementation reranks supplied candidates and does not build an index.
Its query-dependent MLP is not an offline precomputed document-impact index.

## Inputs

Export one JSON object per query to JSONL, with 100 candidates per training query
when reproducing the proposed P1 protocol:

```json
{"qid":"q1","query":{"1":0.8,"7":0.2},"candidates":[{"docid":"d1","concepts":{"1":0.9},"teacher_score":3.2},{"docid":"d2","concepts":{"7":0.5},"teacher_score":0.4}]}
```

Concept keys are nonnegative integer IDs; activations must be finite and
nonnegative. Use the same frozen SAE and sparsification settings for all splits.
Teacher scores must come from the same dense model, scoring convention, and
candidate collection procedure. Labels are independent TREC qrels lines:
`qid 0 docid relevance`. Validation and evaluation do not require teacher scores.

Corpus statistics JSON must describe the **whole indexed corpus**, not the
training candidates. Count each active concept once per document:

```json
{"num_docs":10000,"avg_doc_length":12.5,"document_frequency":{"1":200,"7":350}}
```

The example is illustrative, not a downloadable dataset. Include DF entries for
all concepts that can intersect. IDF is `log(1 + (N - df + .5)/(df + .5))`.

## Commands

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
python3 -m unittest discover -s tests -v

.venv/bin/python -m p1.train --train data/train.jsonl --validation data/validation.jsonl --qrels data/validation.qrels --stats data/stats.json --output artifacts/p1.pt

python3 -m p1.evaluate --data data/validation.jsonl --stats data/stats.json --qrels data/validation.qrels --tune

.venv/bin/python -m p1.evaluate --data data/dev.jsonl --stats data/stats.json --qrels data/dev.qrels --checkpoint artifacts/p1.pt --run-output artifacts/p1.run
```

Evaluation without a checkpoint uses our explicit BM25-style formula:
`sum(q[c] * idf[c] * d[c]*(k1+1)/(d[c]+k1*(1-b+b*length/avg_length)))`.
This formula must be checked against the released implementation before calling
it a reproduced CL-SR baseline. Default parameters are k1=1.2 and b=0.75.
Tuning searches 20 combinations and reports the best validation MRR@10;
pass those chosen `--k1` and `--b` explicitly for held-out evaluation.

## Experimental controls and remaining work

Reserve the team's 5,000 training queries for validation; keep their query IDs
disjoint from scorer training. Never tune on MS MARCO dev or TREC DL. The trainer
selects the best epoch by validation MRR@10 and stores input hashes and settings.
Run files and qrels must have matching query-ID sets to catch accidental split
mismatches. Missing relevant documents stay in the metric denominator.

Compare default BM25-style, validation-tuned BM25-style, and learned scoring
using identical representations and candidate sets. Report MRR@10, NDCG@10,
and Recall@1000. With only 100 supplied candidates, Recall@1000 is limited to
those candidates and should be labeled candidate recall. Dense top-100 reranking
does not establish full-corpus retrieval quality or sparse retrieval efficiency.

Before final project results: obtain upstream code/checkpoints; verify the baseline
formula; export corpus statistics and candidate activations; train with real dense
teacher scores; evaluate over sparse-generated candidates or a full index; measure
latency/index size on fixed hardware; and run paired significance tests on final
query-level results. No retrieval-quality improvements have been measured yet.
